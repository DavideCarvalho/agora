The provider mounts a single route — `POST /payments/webhook/:provider` — and routes the
request to the matching driver, which validates the signature and normalizes the payload.

## Registering endpoints

```sh
node ace payments:webhook
```

prints the exact URL and event list per configured provider. Register them in each
provider's dashboard.

## Validation per provider

Each gateway signs webhooks its own way. Configure the credential in the driver config
(or the env fallback) and the driver enforces it — a request without a valid signature
returns `400` and is never processed.

| Provider | Mechanism | Header | Config / env |
| --- | --- | --- | --- |
| Stripe | HMAC via `constructEvent` | `stripe-signature` | `webhookSecret` / `STRIPE_WEBHOOK_SECRET` |
| AbacatePay | HMAC-SHA256 (base64) | `x-webhook-signature` | `webhookSecret` or `publicKey` / `ABACATE_PUBLIC_KEY` |
| Asaas | Shared token | `asaas-access-token` | `webhookToken` / `ASAAS_WEBHOOK_ACCESS_TOKEN` |
| Woovi | RSA-SHA256 (recommended) | `x-webhook-signature` | `webhookPublicKey` / `WOOVI_WEBHOOK_PUBLIC_KEY` |
| Woovi | Per-webhook HMAC-SHA1 (deprecated) | `X-OpenPix-Signature` | `webhookSecret` / `WOOVI_WEBHOOK_SECRET` |

```ts
export default defineConfig({
  providers: {
    asaas: payments.asaas({ apiKey: env.get('ASAAS_API_KEY'), webhookToken: env.get('ASAAS_WEBHOOK_TOKEN') }),
    woovi: payments.woovi({ appId: env.get('WOOVI_APP_ID'), webhookPublicKey: env.get('WOOVI_PUBLIC_KEY') }),
  },
})
```

### Enforcement policy

- **Credential configured** → strict: requests missing the header, with a wrong
  signature, or with a tampered body are rejected. All comparisons are timing-safe.
- **No credential configured** → verification is skipped for gateways where signing is
  optional (Asaas, AbacatePay, Woovi), so local development keeps working. Stripe
  always requires its secret — events cannot be verified otherwise. Set the credential
  before going to production.

Woovi's recommended `x-webhook-signature` takes precedence over the deprecated HMAC:
when `webhookPublicKey` is set it is enforced, and `webhookSecret` (if also set) is
ignored. The public key accepts PEM or the base64-encoded PEM shown in the dashboard.

## Processing

Once validated, the event flows through the billing layer (when enabled):

1. recorded in `billing_webhook_events` (idempotency — replays are skipped);
2. normalized (`payment.succeeded`, `subscription.canceled`, ...) and synced into the
   billing tables;
3. **your business logic runs** — via the `agora:payments:billing:*` events, via
   `billing.handlers` in the config, or in a controller you write yourself;
4. dispatched through `@adonis-agora/durable` when installed, else in-process with
   exponential-backoff retries.

## Running your business logic — four options

The mounted route guarantees security + sync, but the app's business logic (grant
credits, activate a subscription) needs a home. Pick whichever fits:

### 1. Convention folder `app/payment_handlers/` (durable-style)

Drop a file per event; the provider auto-discovers it (build-time barrel via the
Assembler `init` hook, runtime scan as fallback). Scaffold with:

```sh
node ace make:webhook-handler payment.succeeded
```

```ts
// app/payment_handlers/payment_succeeded.ts
import { inject } from '@adonisjs/core'
import type { WebhookEvent } from '@adonis-agora/payments'

@inject()
export default class PaymentSucceededHandler {
  static readonly eventType = 'payment.succeeded'
  async handle(event: WebhookEvent): Promise<void> {
    // dispatch to a durable workflow / queue — never do heavy work inline
  }
}
```

Register the codegen hook in `adonisrc.ts`:

```ts
hooks: { init: [() => import('@adonis-agora/payments/hooks/webhook_handlers')] }
```

### 2. `billing.handlers` in the config — function or DI service

Handlers run inside `WebhookProcessor.process()`, so a throw marks the event `failed` in
the ledger and triggers the dispatcher's retry:

```ts
// config/payments.ts
import PaymentSucceededHandler from '#payment_handlers/payment_succeeded'

billing: {
  handlers: {
    'payment.succeeded': PaymentSucceededHandler, // DI service (lib calls .handle)
    // or a plain function:
    'payment.refunded': (event) => { ... },
  },
}
```

### 3. Subscribe to the events

The processor publishes the normalized business events on the `@adonis-agora/diagnostics`
bus — `agora:payments:payment.succeeded`, `payment.failed`, `subscription.canceled`, plus
the webhook lifecycle (`webhook.received`/`processed`/`failed`). Subscribe with
`onDiagnostic` (framework-agnostic — works in HTTP, workers, and ace commands):

```ts
// start/payments.ts (preloaded)
import { onDiagnostic } from '@adonis-agora/diagnostics'

onDiagnostic('payments', 'payment.succeeded', ({ payload }) => {
  // payload.externalReference routes to your local record
  // fire-and-forget — a throwing handler does NOT fail the webhook (already ledgered)
})
```

The same events show up in Telescope as `payments` entries (via `@adonis-agora/payments/telescope`).

### 4. Your own controller

Build your own route with `new WebhookProcessor({ store, driver, handlers })` for full
control over the response shape and flow.

### The money-flow pattern: handlers dispatch to durable

Webhooks must respond fast (`200`), and heavy/idempotent work belongs in a queue or a
durable workflow — the handler's only job is to dispatch. With durable's event triggers
(`@adonis-agora/durable` ≥ the `@OnDiagnostic` release) the workflow subscribes itself,
so the handler file disappears entirely:

```ts
@OnDiagnostic({ lib: 'payments', event: 'payment.succeeded' })
export class ProcessPaymentWorkflow extends BaseWorkflow {
  static workflow = { name: 'process-payment' }
  async run(ctx, input) {
    // input is the payment.succeeded payload — durable owns retry + exactly-once
  }
}
```

Without that, a plain handler dispatches via `engine.start` (fire-and-forget):

```ts
@inject()
export default class PaymentSucceededHandler {
  static readonly eventType = 'payment.succeeded'
  constructor(private engine: WorkflowEngine) {}
  async handle(event: WebhookEvent): Promise<void> {
    const externalReference = (event.data as { externalReference?: string }).externalReference
    if (!externalReference) return
    // fire-and-forget: durable owns retry + exactly-once; the webhook responds fast.
    await this.engine.start(ProcessPaymentWorkflow, { externalReference }, randomUUID())
  }
}
```

## Routing payments back to your records (`externalReference`)

Webhook handlers usually need to map a payment to the app's own record (a `Payment`
row, a subscription). Set `externalReference` on the charge/subscription and the gateway
echoes it back — surfaced on the normalized `event.data.externalReference` and the
`payment.succeeded` diagnostics payload, so you never dig into `event.raw`:

```ts
const payment = await Payment.create({ ... })
await driver.charge({
  customerId,
  amount,
  externalReference: payment.id, // echoed back on webhooks
})

// in the listener:
onDiagnostic('payments', 'payment.succeeded', ({ payload }) => {
  const payment = await Payment.find(payload.externalReference)
  // ...
})
```

- **Asaas** → `externalReference` field (propagated to every installment of a
  subscription's charges). Prefer it over `idempotencyKey` (which still doubles as the
  reference when `externalReference` is absent).
- **Woovi** → `correlationID`.
- **Stripe** → `metadata.external_reference`.

## Webhook events

The normalized event types the processor understands:

- `payment.succeeded` / `payment.failed` / `payment.refunded` / `payment.updated`
- `subscription.created` / `subscription.updated` / `subscription.canceled`

Each gateway maps onto these — e.g. Stripe `invoice.payment_succeeded`, Asaas
`PAYMENT_RECEIVED`, AbacatePay `checkout.completed` and Woovi
`PIX_AUTOMATIC_COBR_COMPLETED` all become `payment.succeeded`.
