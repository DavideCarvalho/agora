The billing layer is the Laravel-Cashier experience for AdonisJS: Lucid models + mixins on
your side, and — on the library side — an **idempotent webhook processor** that keeps the
local billing tables in sync with the gateway, plus a dispatcher that runs webhooks
through `@adonis-agora/durable` when it's installed.

The core promise: **your database is always a truthful mirror of the gateway**, no matter
how many webhooks arrive, in which order, or how many times a gateway redelivers them.

## The billing tables

The configure command publishes a migration creating four tables:

| Table | Purpose |
| --- | --- |
| `billing_customers` | the polymorphic link between your users and their gateway customers |
| `billing_subscriptions` | subscriptions — `status`, `plan_id`, `trial_ends_at`, `ends_at` |
| `billing_payments` | every payment, keyed by **gateway id** |
| `billing_webhook_events` | the **idempotency ledger**, keyed by gateway event id |

The last one is the heart: it's what makes every redelivery a no-op instead of a
double-grant.

## The Billable model

Compose `withBillable()` into your user model (or scaffold one):

```sh
node ace make:billable user
```

```ts title="app/models/user.ts"
import { BaseModel, compose, column } from '@adonisjs/lucid/orm'
import { withBillable } from '@adonis-agora/payments'

export default class User extends compose(BaseModel, withBillable()) {
  @column({ isPrimary: true }) declare id: string
}
```

The mixin adds `billingCustomerId` and `billingProvider`, so a user knows which gateway
customer it is — the id every charge/subscription call starts from:

```ts title="app/services/subscribe_service.ts"
const customer = await payments.driver('pix').createCustomer({
  name: user.name,
  email: user.email,
  taxId: user.taxId,
})
user.billingCustomerId = customer.id
user.billingProvider = 'woovi'
await user.save()
```

Getting a gateway customer is so common that the library ships `ensureCustomer` — reuse
the stored id or create at the gateway, whichever applies:

```ts title="app/services/subscribe_service.ts"
import { ensureCustomer } from '@adonis-agora/payments'

const customer = await ensureCustomer(driver, user.billingCustomerId, {
  name: user.name, email: user.email, taxId: user.taxId,
})
user.billingCustomerId = customer.id
await user.save()
```

## Subscriptions

Create a subscription at the gateway; the webhook processor keeps the local row in sync
after that:

```ts title="app/services/subscribe_service.ts"
const subscription = await payments.driver('pix').createSubscription({
  customerId: user.billingCustomerId!,
  planId: 'plan_pro',
  amount: 4990,
  startDate: '2026-09-01',
  externalReference: `sub:${user.id}`,
  invoice: true,
})
```

The processor listens for `subscription.created/updated/canceled` and
`payment.succeeded/failed/refunded` and upserts the local rows automatically — trial
windows, period ends, cancellations all land in `billing_subscriptions` without you writing
a single sync query.

## Webhook processing — why it's safe to trust

The processor's ordering is deliberate. Every event is recorded in `billing_webhook_events`
**before** any work runs. If that gateway event id is already present, processing stops
immediately — so a redelivered webhook (gateways retry on timeout, dashboards re-send, ops
replays from logs) is a no-op, not a second grant.

```ts title="start/payments.ts"
import { onDiagnostic } from '@adonis-agora/diagnostics'

onDiagnostic('payments', 'payment.succeeded', ({ payload }) => {
  // grant access, send receipt — safe to assume this event was seen once
})
```

This is the outer idempotency defense. For the money-critical paths, add an inner one too
(a `WHERE status = pending` update, a unique index on the grant) — defense in depth, not
redundancy. See [Webhooks → The lifecycle](./webhooks#the-lifecycle-of-a-webhook).

<Callout type="info" title="`externalReference` is your routing key">
Sync keeps the *billing tables* correct, but your business logic needs *your* ids. The
`externalReference` you set on the charge/subscription comes back on the webhook and routes
the confirmation to your own `Payment`/`Subscription` rows. See
[Webhooks → externalReference](./webhooks#routing-payments-back-to-your-records-externalreference).
</Callout>

## Durable integration — webhooks survive restarts

A webhook half-way through granting credits is exactly the work that must not be lost on a
deploy or crash. By default (`billing.durable = 'auto'`), webhooks are processed as
**durable workflow runs** when `@adonis-agora/durable` is installed *and* its provider is
registered in the app:

- every step is checkpointed — a crash resumes where it stopped instead of re-running;
- retries are deterministic, not best-effort.

Without durable, the fallback is an in-process dispatcher that retries with exponential
backoff (max 5 attempts, base 500 ms, capped at 30 s) — so a transient failure never loses
a payment notification, though it doesn't survive a process restart the way durable does.

Set `billing.durable: false` to force the in-process dispatcher, or `true` to require
durable (throwing when it's missing).

## Usage-based billing — metered subscriptions

Plans that bill by consumption (API calls, stored GB, minutes) are metered through the
`billing_usage_events` table. Record consumption as it happens, then aggregate per meter
for a period:

```ts title="app/services/usage_service.ts"
// When a metered event happens (an API call, a message sent):
await store.recordUsage({
  subscriptionId: subscription.id,
  meter: 'api_calls',
  quantity: 1,
})

// At the end of the billing period, roll up what to bill:
const report = await store.usageReport({
  subscriptionId: subscription.id,
  from: periodStart,
  to: periodEnd,
})
// [{ meter: 'api_calls', quantity: 412 }]
```

`usageReport` filters by `subscriptionId`, `customerId`, `meter`, and a `from`/`to` window,
aggregating `quantity` per meter — the input to a usage-based invoice or overage charge.
The table and model ship in the published migration; the in-memory store mirrors it for
tests.

## Mixins

`make:billable` composes `withBillable()` — the base. The library also ships narrower
mixins you can stack on other models:

- `withSubscription` — a model that owns recurring subscriptions.
- `withPayment` — a model that owns one-off payments.

Each exposes the corresponding billing-store methods off the model instance, so most
billing code reads as `user.charge(...)`, `user.subscribe(...)` rather than service-layer
calls.
