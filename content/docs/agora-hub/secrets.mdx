---
title: Secrets
description: What can live in the Hub's config server and what must stay in each platform's environment — the bootstrap secrets an app needs before it can reach the Hub.
---

With a Hub, an app's configuration can come from the Hub's config server: versioned, audited,
sealed, changed in one console. But an app needs some values **before** it can reach the Hub, and
the Hub needs some before it can open its own database. Those stay in the platform.

## The rule

A value stays in the platform's environment when the app needs it to boot, to reach the Hub, or to
open data that is already sealed. Everything else can move to the config server.

## On every app

| Stays in the platform (bootstrap) | Can live in the Hub's config server |
| --- | --- |
| `APP_KEY` (and legacy keys): opens sessions, cookies and sealed data | third-party API keys (payments, email, storage, AI) |
| database URL and credentials | feature settings, limits, URLs of other services |
| Redis URL and credentials | webhook signing secrets the app checks |
| password pepper (if the app hashes passwords) | anything the app reads after boot |
| the app's Hub credentials: `AGORA_TENANT_CLIENT_ID`, `AGORA_TENANT_CLIENT_SECRET`, the Hub URL and issuer | |
| `AUTHKIT_CLIENT_ID` / `AUTHKIT_CLIENT_SECRET` (login), when the app needs them at boot | |

Secrets in the config server are sealed before they are stored. A value sealed to one app
(`agora:pk1:…`) can be opened only by that app's private key, which it keeps on disk sealed with
its `APP_KEY`: not even the Hub can read it. Reading secret values needs `config:secrets:read` in
the app's token; plain values need only `config:read`.

To have values in `config/*.ts`, which load before providers boot, fetch them in `bin/server.ts`
with `bootstrapConfig` and a snapshot path, so a restart while the Hub is down still boots. See
[the tenant page](/docs/config/tenant).

## On the Hub

Everything the Hub needs to start stays in its platform environment:

| Variable | Notes |
| --- | --- |
| `APP_KEY` | when the Hub serves an existing identity, a **reference** to that app's `APP_KEY` |
| `PASSWORD_PEPPER` | same: a reference, never a copy |
| `DB_*`, `IDENTITY_DB_*` | references to the database services |
| `REDIS_*` | reference to the Hub's Redis |
| `CRYPTO_ROOT_KEY` | the root that seals crypto's keys; losing it loses every key |
| `AUTHKIT_ADMIN_API_KEY` | only if you use the Admin API |
| social login client id and secret | references to the provider's credentials |
| `ORIGIN_SHARED_SECRET` | the header your CDN adds |
| SMTP credentials | for login emails |

<Callout type="warn" title="Root keys">
`APP_KEY` and `CRYPTO_ROOT_KEY` open the keystore, the TOTP secrets and every crypto key. Back them up
outside the platform. Every replica needs the same values; `node ace agora:doctor` reports a root
that can't open what it should.
</Callout>

## References, not copies

When two services need the same value (the Hub and the app whose identity it serves share
`APP_KEY` and the pepper), make the second one a reference to the first one's variable, if your
platform supports it. Rotating the value in one place then updates both on their next deploy, and
nobody wonders which copy is the real one.
